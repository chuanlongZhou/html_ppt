对，而且我认为这不是“补充一个功能点”，而是应该上升到**项目核心差异化之一**。

你目前的文档主要把 Web 的优势描述为：HTML/SVG、Morph、动态数据、D3/ECharts 等能力；`data-viz` 也主要定义为各种图表类型和 chart specification。:chatgpt-content-reference{index="0"} :chatgpt-content-reference{index="1"}  
但实际上 **Web Presentation 相比 PPT 的一个结构性优势是：visualization 本身可以是一个有状态、可交互、可计算的应用，而不仅仅是一张图。**

我会把这个提升到和 **Presentation IR / Motion Grammar / Component System** 同等级。

## 1. 现在的定义还是偏“Animated PPT”

目前核心链条大体是：

```text
Data
↓
Chart
↓
Slide
↓
Animation
```

但 Web 真正可以做到的是：

```text
Data
↓
Interactive Visualization Model
↓
View State
↓
Interaction
↓
New View State
↓
Animation / Explanation
↓
Analysis
```

区别非常大。

例如一张印度城市排放图，不再只是：

> 显示 100 个城市排放量。

而是一个真正的数据对象：

```text
Map
├── hover city
├── click city
├── filter sector
├── select year
├── compare cities
├── zoom
├── change metric
└── inspect underlying data
```

每一次操作本质上都是：

```text
state A
→ user action
→ state B
```

而你前面已经把 Morph 定义为：

> 信息状态变化。:chatgpt-content-reference{index="2"}

所以这两套东西其实可以统一。

# 2. Presentation Animation 和 User Interaction 本质上可以共享 State System

这是我认为项目可以进一步形成独特架构的地方。

例如：

```yaml
visualization:
  id: india-emissions

  state:
    year: 2024
    sector: total
    selected_city: null
    metric: emissions
```

演讲者推进 presentation：

```yaml
transition:
  set:
    selected_city: Delhi
```

系统自动产生：

```text
India overview
     ↓
zoom Delhi
     ↓
highlight Delhi
     ↓
update charts
```

但听众也可以自己点击 Mumbai：

```text
click Mumbai

state.selected_city = Mumbai
```

然后**使用同一套 State → Render → Motion pipeline**。

因此：

```text
Presentation navigation
User interaction
AI-driven analysis
```

三者都不应该是三个独立系统。

而应该统一成：

```text
State Transition
```

这是一个非常值得写进架构原则的东西。

# 3. 我建议加入一个新的核心概念：Interactive Visualization

不要只叫 `Chart`。

比如：

```text
Visualization
├── Data
├── Encoding
├── State
├── Interaction
├── Selection
├── Filter
├── Transform
├── Annotation
├── Motion
└── View
```

一个 specification 可以类似：

```yaml
component: CityEmissionMap

data:
  source: city-emissions.csv

encoding:
  geography: city
  color: emission
  size: population

state:
  year: 2024
  sector: total
  selected_city: null

interaction:

  hover:
    show:
      - city
      - emission
      - population

  click:
    set:
      selected_city: $city

  controls:
    year:
      type: slider

    sector:
      type: select
```

那么 AI 并不需要写 D3 `onclick()`。

AI 只声明：

> 用户可以选择 city。

renderer / component 自己实现 interaction。

这与你现有“semantic component 优先于 low-level HTML”的原则完全一致。:chatgpt-content-reference{index="3"}

# 4. 更重要的是：Presentation Mode 和 Exploration Mode

我甚至建议把这个写进产品核心概念。

## Presentation Mode

演讲过程中：

```text
Presenter controls narrative.
```

比如：

```text
Next
↓
2020 → 2022
↓
India → Delhi
↓
Total → Power sector
```

所有操作按照设计好的 narrative path 自动进行。

---

## Exploration Mode

讲完这一页之后：

```text
Audience / presenter controls visualization.
```

可以：

```text
hover
click
filter
zoom
change year
change metric
compare
```

也就是说一张 slide 可以有两种状态：

```text
guided narrative
      ↓
free exploration
```

这个 PPT 几乎无法优雅做到。

而 Web 非常自然。

# 5. 这会直接改变“动画”的设计方式

传统 PPT：

```text
animation = timeline
```

例如：

```text
0s fade map
1s move map
2s show chart
```

但 Web interactive presentation 更应该：

```text
animation = state transition
```

例如：

```text
year:
2020 → 2021
```

图表自行：

```text
bars change height
map colors interpolate
labels update
ranking reorder
```

或者：

```text
selected_city:
null → Delhi
```

然后：

```text
map zoom
Delhi highlight
other cities de-emphasize
time-series appears
```

所以你目前的 Motion Grammar 最终可以扩展成：

```text
State Transition Grammar
```

Motion 只是 state transition 的视觉表现。

这是比“支持更多 PowerPoint animation”更高级的设计。

# 6. Interactive Chart 不应该局限于自己内部

还有一个更大的能力：

## Linked Views

例如一页同时有：

```text
India map
+
city ranking
+
time series
+
sector breakdown
```

点击 Delhi：

```text
Map
 selected = Delhi
       │
       ├──→ ranking highlights Delhi
       ├──→ time series loads Delhi
       └──→ sectors update Delhi
```

也就是类似：

```text
Crossfilter / linked brushing
```

这种设计对科研 presentation 极其有价值。

Presentation 就开始接近一个：

> lightweight visual analytics system。

而不是 slides。

# 11. Component contract 也需要加入 Interaction Capability

我上一条说 component 应该定义：

```text
semantic input
layout behavior
motion behavior
```

这里现在应该扩成：

```text
data contract
state contract
interaction contract
motion contract
```

例如：

```yaml
LineChart:

  interactions:
    hover: true
    select-point: true
    brush-x: true
    zoom-x: true

  state:
    highlighted_series:
    selected_range:

  motion:
    data-update: true
    domain-change: true
    series-enter: true
```

Map：

```yaml
Map:

  interactions:
    hover-region: true
    select-region: true
    pan: true
    zoom: true

  state:
    selected_region:
    zoom_level:
    active_layer:
```

这之后 AI 才能真正“设计交互”，而不是写 JS。

# 12. 需要一个很重要的约束：Narrative state ≠ Exploration state

这是实现时很容易踩坑的地方。

假设 presenter 已经设计：

```text
State 1 → State 2 → State 3
```

用户在 State 2 自己点击了一堆东西。

然后 presenter 按 Next。

系统必须知道：

```text
是从用户当前 state
→ State 3

还是 reset 到 authored State 2
→ State 3？
```

因此至少需要：

```text
Authored State
Exploration State
```

甚至：

```text
base_state
presentation_state
interaction_state
```

最后 render state：

```text
effective_state =
base
+ presentation overrides
+ interaction overrides
```

这是一个应该在 architecture 阶段定义好的问题。
